## 1. Запрошено и не сделано

### 1.1 Режимы конфигурации стола ✅

Запрос: «реализована ли конфигурация высоты стола по одной кнопке с автоматическим оффсетом по z?
добавь разные конфигурации стола по кнопке, по 4 точкам где расположены винты, по пути 3d touch
но с выключенным, и по пути 3d touch но чтобы он уже работал».

Сейчас есть одна кнопка: `G28` → `G29` → `M420 S1` → `M500` → контрольное чтение. Режимов нет,
автоматического Z-offset нет.

| Режим | Что должен делать | Статус |
|---|---|---|
| **По 4 точкам винтов** | `G30 X.. Y..` в каждой точке винта → точные высоты вместо интерполяции по сетке | ✅ подсказки считаются по фактическим точкам; молчание зонда = отказ, а не ноль; при неполном замере подсказки не показываются |
| **3D Touch, компенсация выключена** | Полная сетка `G29`, но `M420 S0`: только измерить | ✅ `M420 S0` ставится явно, `M500` пропускается с объяснением |
| **3D Touch, компенсация работает** | Текущее поведение `autoConfigureBed` | ✅ |
| **Полуавтомат Z-offset** | `M851 Z0` → `G28` → центр → `Z0` → тест бумагой → фиксация с `M500` | ✅ отмена возвращает прежний offset |
| **Автоматический Z-offset** | см. ниже | ⛔ физически невозможно, обоснование ниже |

**⛔ Автоматический Z-offset зондом невозможен, и это физика, а не лень.** BLTouch знает только,
на какой высоте сработал его щуп. Где находится кончик сопла, он не знает — между щупом и соплом
есть механическое смещение, которое и есть `M851 Z`. Вывести его из показаний самого зонда нельзя:
уравнение содержит две неизвестных, а измерение одно. Нужна внешняя точка отсчёта — бумага, датчик
контакта сопла или индикатор.

**Что честно автоматизируется — полуавтомат в одну кнопку и одно физическое действие:**
`G28` → `G30` в центре стола (получаем высоту срабатывания щупа) → сопло опускается в точку
контакта → пользователь делает тест бумагой и жмёт «зафиксировать» → приложение считает и пишет
`M851 Z`, затем `M500` и контрольное чтение. Это лучше текущего ручного babystep и не обещает
невозможного.

### 1.2 Интеграция со слайсером 🔨 начато, отложено

Запрос: «необходимо добавить интеграцию с слайсерами например cura, чтобы он не переписывал
настройки принтера, либо во время конфигурации писать настройки сразу параллельно в слайсер
(а то поставлю пресет pla а разогреется при печати до petg)».

**Уточнение диагноза.** Cura сама по себе EEPROM не перезаписывает. Реальные причины расхождения
две, и они разные:

1. **Температура из файла всегда побеждает.** При печати с SD стартовый блок G-code содержит
   `M104`/`M140` из профиля материала слайсера, и Marlin их исполняет. Пресет, выставленный в
   3DTune, — это предварительный нагрев и ручная работа, а не то, чем будет печататься файл.
   Хост не может это запретить: во время печати файл авторитетнее.
2. **Стартовый G-code может содержать команды калибровки.** Некоторые вендорские профили пишут
   `M92`/`M301`/`M851`/`M500` в старт. Вот это действительно затирает калибровку, причём
   безвозвратно.

**План работ:**

| Пункт | Что делать | Статус |
|---|---|---|
| Анализ стартового G-code | Пользователь вставляет свой start/end блок, 3DTune разбирает: команды, затирающие калибровку (`M92`/`M301`/`M304`/`M851`/`M500`/`M502`); температуры (то есть под какой пластик этот профиль на самом деле); `M201`/`M203`/`M204`/`M205` выше лимитов прошивки; `G29` на каждой печати (износ щупа и время) | ✅ карточка «Разбор G-code слайсера», start и end, работает без подключения |
| Предупреждение о расхождении температур | Во время печати сравнивать живые цели с выбранным пресетом и предупреждать: «печатается файл на 240 °C, а выбран PLA 205 °C — тот ли это файл» | ⬜ |
| Экспорт машинных настроек в Cura | Из `M503` собрать значения для Machine Settings: размер стола, максимальные скорости, ускорения, jerk — чтобы слайсер не планировал за пределами прошивки | ⬜ |
| Генерация рекомендованного стартового блока | По фактическому состоянию принтера: есть ли сетка, включена ли компенсация, есть ли зонд | ⬜ |

**Что уже проверяет разбор** (`src/printer/slicer.ts`, карточка в UI, RPC `analyzeStartGcode`):

- затирание калибровки — `M92`/`M301`/`M304`/`M851`/`M206`/`M900`. Уровень зависит от того, есть ли
  ниже `M500`: без него это сессионная подмена (⚠), с ним — запись в EEPROM (✕). Отдельно `M500`
  (износ flash + фиксация чужих значений), `M502` (заводской сброс), `M501` (отбрасывает
  несохранённое из 3DTune);
- температуры: максимум по `M104`/`M109`/`M140`/`M190`, определение пластика по ближайшему пресету
  и прямое сравнение с выбранным в 3DTune — это и есть исходная жалоба «поставлю PLA, а разогреется
  до PETG». Превышение рабочего потолка (`limits.hotendMax`/`bedMax`) — критично;
- `M201`/`M203`/`M204`/`M205` против фактического `M503`. Без подключения проверка честно
  сообщает, что сравнивать не с чем, а не молчит. У `M205` сравниваются только X/Y/Z/E/J:
  `S`/`T` — минимальные подачи, `B` — минимальное время сегмента, «превышения» там не бывает;
- `G29` без параметров на каждой печати (время + износ щупа). `G29` **с** параметром не судится, а
  объясняется: смысл зависит от алгоритма левелинга, а он компилируемый. В комьюнити-сборке
  (`reference/kp5l-marlin-2.1.1-abl`) включён **UBL**, где `G29 L<слот>` загружает сетку без
  зондирования; на сборке с BILINEAR или MBL тот же параметр игнорируется и это полный прогон;
- `G29`/`G30` до `G28`, отсутствие `G28`, выдавливание до `M109`, нагрев сопла раньше стола.
  Отсутствие `G28` считается проблемой только у блока, который **греет**: конечный блок двигается
  без парковки совершенно правомерно, и обвинять его не в чем;
- `M906`/`M907` — на TMC2225 в standalone они не действуют;
- подстановки слайсера (`{material_print_temperature}`, `[first_layer_temperature]`) распознаются
  как подстановки, а не как отсутствие нагрева.

Совет по левелингу в разборе намеренно **не** говорит «добавь `M420 S1`» — см. факт ниже.

**⚠️ Установленный факт, который нельзя забыть.** По исходнику Marlin (`G28.cpp:301`) `G28`
**безусловно выключает** компенсацию стола, а восстанавливает её только при
`RESTORE_LEVELING_AFTER_G28` или `ENABLE_LEVELING_AFTER_G28`. В комьюнити-конфиге KP5L
`RESTORE_...` выключен, но **`ENABLE_LEVELING_AFTER_G28` включён** — значит на этой сборке
компенсация после `G28` остаётся. Поэтому совет «добавь `M420 S1` в старт слайсера» для этой
прошивки **неверен**. На стоковой прошивке поведение неизвестно и проверяется эмпирически:
`G28`, затем `M420` — посмотреть, включена ли компенсация.

## 3. Отложено осознанно

Это решения, а не забытое. Каждое с причиной, чтобы не пересматривать по кругу.

| Пункт | Почему отложено |
|---|---|
| **Печать с ПК** (стриминг G-code) | CH340 @ 115200 + `BUFSIZE 4` — самое слабое звено, обрыв USB убивает печать. Печатаем с SD; мониторинг прогресса печати — в планах, стриминг — нет |
| **Сборщик прошивки** (генерация `Configuration.h` + PlatformIO) | Большая фича. И залить по USB всё равно нельзя: бинарь шифруется под MKS-загрузчик, только SD |
| **Native USB CDC** (`USB_MOD`, ~1.5 Мбит/с) | Требует аппаратной переделки: перекинуть эндстопы Y/Z-min с PA11/PA12 на PB10/PB11 |
| **Режим Web Serial** (страница без сервера) | Safari и Firefox не поддерживают, и USB всё равно нужен там же, где браузер |
| **Доступ из интернета** | Сознательный отказ. Управление нагревателями наружу не выставляем. Нужен — только VPN, на своей ответственности |
| **Камера и таймлапс** | Не запрашивалось; архитектура не мешает добавить |
| **Klipper** | `klippy` только Linux; на Windows WSL2 + usbipd хрупко, macOS не поддерживается. Требование Windows + macOS это убивает |
| **Мастера Фазы 4**: поток, температурная башня, тест Linear Advance, ускорения/jerk, откаты | Требуют печати тестовых моделей и слайсера. Поток помечен в мастере как «хост этого не умеет» честно |
| **Фаза 5**: mDNS (`3dtune.local`), PWA-манифест, автозапуск службой, single-file бинарь | Пейринг по коду закрыл основную боль; остальное — удобство |

## 4. Заблокировано железом 🔒

Ничего из этого нельзя закрыть без принтера под рукой.

| Пункт | Что нужно |
|---|---|
| **[Фаза 0](PHASE0_DISCOVERY.md) — разведка на живом принтере** | 20 минут. **Гейт перед первым нагревом и движением.** Определяет, даёт ли стоковая прошивка нормальный GCode-контракт и переживает ли `M500` выключение питания |
| **S7 / S11 — лимиты температур** | Marlin не отдаёт `HEATER_0_MAXTEMP`/`BED_MAXTEMP` по serial. Сейчас это зашитое допущение (265/110), переопределяемое через конфиг. Сверить с прошивкой |
| **T9 — регрессионный прогон** | [HARDWARE_REGRESSION](HARDWARE_REGRESSION.md) написан, но **ни разу не выполнялся** |
| **U8 — реальный iOS Safari** | Нужен iPhone/iPad. Эмуляция ширины 375px пройдена, это не то же самое |
| **Windows: первый реальный запуск `.bat`** | Скрипт написан и вычитан, но исполнялся только на macOS-стороне (`--doctor`, `.command`). Самое вероятное место спотыкания — брандмауэр Windows |
| **LAN с отдельного устройства** | Проверено на реальном сетевом адресе, но с той же машины. Мак/телефон как отдельный клиент — не проверено |
| **3D Touch: физическое подключение** | Зонд на Z-MAX (`PC4`), управление `PA8`. Выведен ли `PA8` на разъём — проверяется глазами |
| **Направление винтов стола** | Допущение: шаг 0.5 мм (M3) и «затянуть» опускает стол. Проверить один раз, при несовпадении поменять `bedScrews.tighteningLowersBed` в конфиге |
