# 3DTune — план работы

Desktop-приложение (Windows + macOS) для полного управления и настройки Kingroon KP5L
по USB, чтобы не трогать тачскрин принтера.

Технические обоснования — в [RESEARCH.md](RESEARCH.md). Первый шаг — [PHASE0_DISCOVERY.md](PHASE0_DISCOVERY.md).

---

## 1. Вердикт: реализуемо, и не особо сложно — но с одной честной оговоркой

**Реализуемо.** ~85 % задачи — это обычный Marlin-хост: последовательный порт, GCode-протокол,
формы над `M503`. Всё документировано, всё делали до нас. Ничего исследовательского.

**Сложность:** средняя. Не сложность алгоритмов, а сложность *аккуратности* — вся боль в
транспортном слое (§4). Хосты для Marlin ломаются не на UI, а на `Resend:`, `busy:` и таймаутах.

**Оговорка, которую надо принять сразу.** Задумка сформулирована как «по совместительству
прошивка, принтер в симбиозе с ПК». Так делать не нужно и вредно. 3DTune — это **хост, а не
прошивка**. Стандартный GCode-контракт Marlin уже даёт полный доступ к машине; своя прошивка
добавляет только риск окирпичивания и потерю совместимости со слайсерами.

И следствие: **часть настроек физически не меняется по USB.**

| Живое, из приложения, навсегда | Только пересборка прошивки |
|---|---|
| шаги/мм, скорости, ускорения, jerk (`M92`/`M203`/`M201`/`M204`/`M205`) | **существует ли BLTouch вообще** и на каком пине |
| PID сопла и стола + автотюн (`M301`/`M304`/`M303`) | алгоритм левелинга (BILINEAR / UBL / MBL) |
| Z-offset зонда (`M851`), живая подстройка (`M290`) | наличие Input Shaping, Emergency Parser, Host Actions |
| снятие / включение / правка сетки (`G29`, `M420`, `M421`) | `HEATER_0_MAXTEMP`, `BED_MAXTEMP`, thermal protection |
| Linear Advance (`M900`), home offset (`M206`) | распиновка, тип термистора, кинематика |
| сохранить / загрузить / сброс (`M500`/`M501`/`M502`) | поведение тач-UI |
| диагностика (`M119`, `M43`), джог, температуры, макросы | |

**Главный ask — «3D Touch из одного приложения» — стоит ровно на этой границе:** *включить* его
по serial нельзя, а *всё после включения* — можно и полностью. Поэтому сценарий такой:

> одна прошивка с SD-карты один раз → дальше приложение владеет зондом, оффсетами,
> сеткой и калибровкой навсегда.

Kingroon публикует готовый `.bin` с BLTouch, есть проверенные комьюнити-сборки → **компилятор
на первую фазу не нужен**. И: прошивку шить по USB нельзя в принципе (бинарь шифруется под
MKS-загрузчик, `board_build.encrypt_mks`), обновление прошивки навсегда остаётся SD-операцией.

**Оценка трудозатрат** (один разработчик):
- рабочий MVP (связь + температуры + джог + терминал + PID-автотюн + safety + доступ с телефона) —
  **2.5–3.5 недели**
- полноценное приложение по этому плану — **2–3 месяца**
- Фаза 0 (разведка на железе) — **20 минут**, но она **не блокирует** старт разработки:
  Фаза 1 пишется против встроенного эмулятора Marlin, без принтера и без кабеля

## 2. Что известно про железо (кратко)

- Плата: **MKS Robin Nano V1.x**, STM32F103VET6, драйверы TMC2225 **standalone** →
  токов по `M906`/`M913` не будет, это не программируемо.
- Канал связи: `SERIAL_PORT 3` (USART3) → **CH340 → USB, 115200**. Штатно, без модов.
- Тачскрин **не занимает UART** (FSMC/SPI, UI внутри Marlin) → USB-канал наш целиком.
- Есть **второй свободный канал** `SERIAL_PORT_2 1` (гребёнка WIFI) — резерв.
- **EEPROM эмулируется во flash, 2 КБ, ~10 000 циклов стирания.**
- Стол 300×300, Z 330. В стоковом конфиге: `PIDTEMPBED 0` (стол в bang-bang!),
  `BLTOUCH 1`, зонд на **Z-MAX** (`PC4`), управление зондом `PA8`, offset X27 Y−6 Z0.
- В комьюнити-Marlin для KP5L **`PID_AUTOTUNE_MENU` и `PID_EDIT_MENU` выключены** — то есть
  PID на KP5L сейчас с экрана не настроить физически. Прямое обоснование проекта.

## 3. Архитектура: сервер + браузер (web-first)

### Сначала — важное ограничение, которое web не убирает

Доступ по локальной сети **не отменяет USB-кабель**. Кто-то один должен физически держать
последовательный порт: серверу нужен `/dev/cu.usbserial-*` или `COMx`. Браузер на другом
устройстве — это клиент, а не второй канал к плате.

Поэтому «на маке нет USB» решается не веб-мордой, а тем, **какая машина держит кабель**:

| Вариант | Что нужно | Итог |
|---|---|---|
| **Windows-ПК держит кабель** ⭐ | ничего покупать не надо | ядро на ПК, мак/телефон/планшет — клиенты в браузере. **Ровно то, что нужно** |
| Мак держит кабель | **кабель USB-C → USB-B** (~₽500), не переходник-донгл | ядро на маке, всё остальное — клиенты |
| Отдельный мини-хост (Raspberry Pi, старый ноут, мини-ПК) | железка | принтер доступен даже когда основной ПК выключен (модель OctoPrint) |

Если Windows-ПК всё равно стоит рядом и включён, пока идёт печать — первый вариант бесплатный и
лучший. Нативное macOS-приложение при этом становится **необязательным**: мак работает через
браузер, как телефон.

### Схема

```
             ┌──────────── любое устройство в локальной сети ────────────┐
             │  мак (Safari)   телефон   планшет   другой ПК             │
             └──────┬──────────────┬─────────┬──────────┬───────────────┘
                    │  HTTP + WebSocket, http://<ip-хоста>:8420
                    ▼              ▼         ▼          ▼
        ┌──────────────────────────────────────────────────────────┐
        │  3dtune-core   (один процесс на машине с кабелем)        │
        │  ─ раздаёт web-UI (статика)                              │
        │  ─ WS API: стрим состояния + команды                     │
        │  ─ владеет serial-портом, протокольный автомат           │
        │  ─ единая модель состояния + слой безопасности           │
        │  ─ токен-авторизация, аудит «кто что послал»             │
        └──────────────────────────────────────────────────────────┘
                                   │ USB / CH340 / 115200
                                   ▼
                             Kingroon KP5L
```

Одно ядро — много клиентов. Состояние живёт **в ядре**, клиенты его только отражают, поэтому:
- закрыл вкладку на телефоне — печать и нагрев не пострадали;
- открыл на маке и на телефоне одновременно — видят одно и то же, изменения прилетают обоим;
- нативное приложение (если понадобится) становится просто ещё одним клиентом того же API.

### Стек

**Решение: TypeScript / Node для ядра, web-UI — статика без сборки.**

> Это изменение относительно первой версии плана, и причина конкретная: там главным аргументом
> за Tauri+Rust была нотаризация macOS для подписанного `.app`. При web-first подходе на маке
> вообще не запускается приложение — только браузер. Аргумент испарился, остаётся аргумент за
> скорость разработки.

- ядро: **Node + TypeScript**, `serialport` (зрелый, есть prebuilt под win/mac), `fastify` + `ws`
- web-UI: HTML + ES-модули + canvas-графики, **без бандлера и без CDN** — открывается как есть,
  работает офлайн, ничего не собирать
- типы общие для сервера и клиента (один TS-проект)
- `printcore` из Printrun **читаем как спецификацию** протокола (оттестирован годами),
  но не тащим как зависимость — логики там ~600 строк

Что осталось на будущее, если захочется нативную обёртку: **Tauri v2** поверх того же API
(веб-UI переиспользуется целиком) либо `node --experimental-sea` для single-file бинаря.

### Про Web Serial API — почему не он

В Chrome/Edge есть [Web Serial API](https://developer.mozilla.org/en-US/docs/Web/API/Web_Serial_API):
браузер может сам открыть COM-порт, и тогда сервер не нужен вообще — чистая веб-страница.
Соблазнительно, но:

- **Safari не поддерживает** (и Firefox тоже) — то есть на маке не заработает;
- всё равно требует физический USB **на той машине, где открыт браузер** → исходную проблему
  не решает;
- страница закрыта → связь оборвана посреди печати; нет фонового процесса, нет реконнекта.

Оставлено как опциональный режим «без установки» на потом (§5, отложенное).

## 4. Транспортный слой — здесь весь риск

Это то, что отличает «работает» от «глючит раз в час». Каждый пункт — отдельная задача с тестом.

1. **Нумерация строк + чексумма.** `N<line> <cmd>*<xor>`; ресинк через `M110 N0`.
2. **`Resend: N`.** Держать окно отправленных команд, при `Resend:` откатиться и переслать
   с этой строки. Без этого — тихие потери команд.
3. **Пейсинг по `ok`.** При `BUFSIZE 4` / `TX_BUFFER_SIZE 0` нельзя лить команды потоком.
   С `ADVANCED_OK` — считать реальную глубину из `ok N.. P.. B..`.
4. **`echo:busy: processing`.** Keepalive, **не таймаут**. Приходит во время `G28`, `G29`, `M109`,
   `M303`. Классический баг — оборвать связь посреди автотюна.
5. **`Error:` без последующего `ok`.** Отдельная ветка автомата, иначе очередь встаёт навсегда.
6. **Идемпотентное подключение.** Открытие порта может ресетить плату (проверяется в Фазе 0).
   Поэтому после каждого коннекта **всегда** заново: `M115` → `M503` → `M851` → `M420 V1`.
   Никогда не полагаться на состояние из прошлой сессии.
7. **Автодетект фич через `M115` `Cap:`.** UI прячет то, чего в прошивке нет, вместо того чтобы
   отправлять команды в пустоту.
8. **Температуры через `M155 S1`,** а не polling `M105`.
9. **macOS: `/dev/cu.*`, никогда `/dev/tty.*`.** `tty.*` дёргает DTR при открытии.
10. **Реконнект и watchdog.** Обрыв USB → зафиксировать состояние, показать, при возврате
    переиграть п. 6.
11. **Аварийный путь.** `M112` вне очереди. Работает как надо только с `EMERGENCY_PARSER`.

### Слой безопасности (в ядре, не в UI)

- потолки температур из конфига машины, клампинг перед отправкой;
- запрет экструзии при `T < 170 °C`;
- подтверждение на всё, что двигает Z вниз или греет выше 250 °C;
- «мёртвый человек»: если все клиенты отвалились, а нагрев включён — ядро держит нагрев, но пишет
  предупреждение и по таймауту (настраиваемо) может остудить;
- **явная кнопка «Сохранить в принтер», никакого автосохранения** — flash-EEPROM 2 КБ, ~10 000
  циклов; изменения батчить в один `M500`; показывать счётчик записей за сессию.

**Клампинг делает сервер, а не клиент.** Браузерная валидация — только UX. Любая команда из WS
проходит те же проверки, что и локальная: клиенту не верим никогда.

### Безопасность доступа по локальной сети

Открывая управление принтером в сеть, мы открываем **управление нагревателями**. Требования, а не
пожелания:

1. **По умолчанию слушаем `127.0.0.1`.** Выход в локальную сеть — осознанный флаг
   (`--host 0.0.0.0`), а не поведение из коробки.
2. **Токен обязателен.** При первом старте генерируется случайный токен, сохраняется в
   `~/.3dtune/config.json`, печатается в консоль и показывается QR-кодом для телефона.
   Без валидного токена WS-соединение закрывается, HTTP отдаёт 401. Никакого «открыто всем в
   локалке».
3. **В интернет не выставляем. Никогда.** Никаких инструкций по port forwarding в документации.
   Если нужен доступ извне — только через VPN/Tailscale, это ответственность пользователя.
   При старте с `--host 0.0.0.0` — громкое предупреждение в консоли.
4. **HTTP по локальной сети — открытый текст**, включая токен. На домашнем Wi-Fi это приемлемый
   риск, но он должен быть **написан явно**, а не умолчан. Опция самоподписанного TLS — на потом
   (браузерные предупреждения делают UX хуже, чем польза).
5. **Лимит частоты** на команды нагрева и на `M500`.
6. **Аудит:** каждая команда логируется с идентификатором клиента (IP + ярлык устройства).
   Когда управляют с трёх устройств, «кто выставил 260 °C» должно быть видно.
7. **Идентификация устройств:** клиент при подключении присылает ярлык («мак», «телефон»),
   он виден остальным. Без этого мультиклиент превращается в путаницу.
8. **E-Stop тоже под токеном.** Соблазнительно оставить его открытым, но тогда любой в сети может
   срывать печать.

## 5. Фазы

### Фаза 0 — разведка (~20 минут, без кода) 🔒 гейт

См. [PHASE0_DISCOVERY.md](PHASE0_DISCOVERY.md). Ответы дают ветку A / B / C.
**Ничего не начинаем, пока не пройдено.** Если `M500` не сохраняет или `M115` не отдаёт `Cap:` —
Фаза 1 начинается с прошивки, а не с кода.

*Выход:* заполненный чек-лист + дампы `M115`/`M503` в `reference/live/`.

### Фаза 1 — ядро, связь и web-UI (1.5–2 недели)

- `3dtune-core`: обнаружение портов, коннект, транспорт по всем 11 пунктам §4
- **встроенный эмулятор Marlin** — разработка и тесты без принтера вообще
  (`--mock`): температуры с тепловой моделью, `ok`/`busy:`/`Resend:`, `M115` с `Cap:`, `M503`,
  `M155`-автоотчёт, имитация `M303`

  > Эмулятор проверяет **протокол и плумбинг**, не термодинамику. Логику `M303` всё равно
  > валидируем на живом принтере. (Альтернатива/дополнение — сборка Marlin `native_sim`.)
- HTTP + WS сервер, раздача web-UI, токен-авторизация, QR для телефона
- web-UI: подключение, живые температуры + график, терминал, джог XYZE, home, `M84`, эндстопы
- STOP/E-Stop, слой безопасности, мультиклиент с ярлыками устройств
- доступ по локальной сети с телефона проверен на живом Wi-Fi

*Выход:* с телефона в браузере видно температуры и позицию, работает джог и терминал;
связь держится 30+ минут без разрывов; закрытая вкладка ничего не ломает.

### Фаза 2 — конфигурация и PID (1–1.5 недели)

- парсер `M503` → типизированная модель настроек
- редактор настроек формами: шаги/мм, скорости, ускорения, jerk, home offset, Linear Advance
- diff «в принтере / в приложении» + явное «Сохранить» (`M500`), «Загрузить» (`M501`),
  «Заводские» (`M502` + подтверждение)
- профили: экспорт/импорт настроек в JSON, «до/после»
- **мастер PID:** температура, число циклов → `M303 E0 S220 C8 U1`, живой график колебаний,
  парсинг `bias:/d:/Ku:/Tu:/Kp:/Ki:/Kd:`, применение `M301` → `M500`
  - цель **«сопло»** — работает на стоковой прошивке
  - цель **«стол»** — заблокирована в UI, пока `M115` не отдаст поддержку `M304`.
    В стоковом cfg `PIDTEMPBED 0` (bang-bang), т. е. эта цель открывается только после
    прошивки профилем 3DTune (`PIDTEMPBED`, P0 в §6). UI прячет её по `Cap:`-детекту, а не
    отправляет `M304` в пустоту
- `M119` — панель эндстопов в реальном времени

*Выход:* PID **сопла** настраивается полностью из приложения и переживает выключение питания.
Экран не трогали ни раз. PID стола — после Фазы 3/прошивки.

### Фаза 3 — 3D Touch (1–1.5 недели)

Предусловие: прошивка с BLTouch (готовый `.bin` от Kingroon либо профиль 3DTune, см. §6).

- диагностика зонда: деплой/стоу (`M280 P0 S10 / S90`), self-test, статус по `M119`
- `M851` — редактирование XYZ-offset зонда
- **мастер Z-offset:** `G28` → подвод в центр → живая подстройка `M290 Z±0.01` по «бумажке»
  → фиксация в `M851` → `M500`
- `G29` с прогресс-баром и живой картой; визуализация сетки (heatmap + 3D)
- `M420 S1` / `S0`, fade height, точечная правка `M421 I.. J.. Z..`
- советы по подкрутке винтов стола из данных сетки (аналог bed tramming)

*Выход:* установка и полная настройка 3D Touch с нуля без единого касания экрана.

### Фаза 4 — мастера калибровки (1–2 недели)

- E-steps (100 мм → замер → пересчёт `M92 E`)
- поток / flow rate
- Linear Advance (`M900 K`) с генерацией тестового паттерна
- ускорения / jerk
- retraction, PA/температурные башни
- макросы: сохранённые последовательности + `GCODE_MACROS` в прошивке
- диагностика: `M43` (пины), просмотр SD (`M20 L`), логи сессии

### Фаза 5 — упаковка и релиз (1 неделя)

- **Хост-машина** (та, что с кабелем): автозапуск сервера, иконка в трее, «открыть в браузере»
  - Windows: установщик + подсказка про драйвер CH340; автостарт как служба/задача
  - macOS: `launchd`-агент; подсказка про CH340-драйвер и `/dev/cu.*`
  - single-file бинарь (`node --experimental-sea`) чтобы не требовать установленный Node
- **Клиенты:** ничего не устанавливается, только браузер. PWA-манифест → иконка на домашнем
  экране телефона, полноэкранный режим
- mDNS/Bonjour → `http://3dtune.local:8420` вместо запоминания IP
- локализация (ru/en), сбор ошибок

> Нативное приложение под macOS в этой схеме **не нужно**. Если позже захочется — Tauri v2
> поверх того же API, веб-UI переиспользуется целиком.

### Отложено сознательно

| Фича | Почему не сейчас |
|---|---|
| **Печать с ПК** | CH340 @ 115200 + `BUFSIZE 4` — самое слабое звено; обрыв USB убивает печать. Печатаем с SD, приложение занимается настройкой/тюнингом/мониторингом. Мониторинг прогресса печати с SD (`M27`) — **входит** в план, а вот стриминг GCode с ПК — нет |
| **Сборщик прошивки** (генерация `Configuration.h` + вызов PlatformIO) | Реальная и полезная фича, но большая. И залить по USB всё равно нельзя — бинарь шифруется под MKS-загрузчик, только SD |
| **Native USB CDC** (`USB_MOD`, ~1.5 Мбит/с) | требует аппаратной переделки: перекинуть эндстопы Y/Z-min с PA11/PA12 на PB10/PB11 + развести USB D+/D− |
| **Режим Web Serial** (веб-страница без сервера) | Safari и Firefox не поддерживают, и физический USB всё равно нужен там же, где браузер. Не решает исходную проблему (§3) |
| **Доступ из интернета** | Сознательно нет. Управление нагревателями наружу не выставляем. Кому надо — VPN/Tailscale, на своей ответственности |
| **Камера / таймлапс** | не запрашивалось; архитектура не мешает добавить позже |

## 6. Профиль прошивки «3DTune для KP5L»

База: комьюнити-Marlin 2.1.x для KP5L (конфиги лежат в
[`reference/kp5l-marlin-2.1.1-abl/`](../reference/kp5l-marlin-2.1.1-abl/)).
Поверх него:

| Define | Зачем | Приоритет |
|---|---|---|
| `EMERGENCY_PARSER` | сейчас **выключен**. Без него `M112`/`M410`/`M108` стоят в очереди за буфером. Для приложения, которое гоняет сопло на 240 °C восемь циклов `M303`, кнопка STOP с задержкой — **дефект, а не неудобство** | **P0** |
| `ADVANCED_OK` | реальная глубина буфера в `ok`; при `BUFSIZE 4` / `TX_BUFFER_SIZE 0` без неё корректный пейсинг не сделать | **P0** |
| `AUTO_BED_LEVELING_BILINEAR` **вместо** `AUTO_BED_LEVELING_UBL` | UBL требует явных `G29 S<slot>`/`G29 L<slot>`, а число слотов зависит от остатка 2 КБ flash-EEPROM и **может быть нулём**. BILINEAR хранит сетку внутри блока `M500`, управляется `G29` / `M420 S1 V1` / `M421` — приложению владеть этим кардинально проще | **P0** |
| `EEPROM_SETTINGS` | уже включён — не выключать | P0 |
| `HOST_ACTION_COMMANDS` + `HOST_PROMPT_SUPPORT` | принтер сам просит подтверждение у хоста (`//action:prompt_*`) | P1 |
| `AUTO_REPORT_POSITION`, `M114_DETAIL` | живая позиция без polling | P1 |
| `PIDTEMPBED` | в стоковом cfg **стол в bang-bang** → `M304`/`M303 E-1` недоступны вообще, пока не включим. Без этого «PID стола» в мастере Фазы 2 — мёртвая кнопка | **P0** |
| `GCODE_MACROS` | макросы на стороне прошивки | P2 |
| Урезать тач-UI до статус-дисплея | ты хочешь «совсем не трогать экран». Заодно снимает риск: тачскрин — **равноправный источник команд**, Marlin не умеет блокировать LCD на время работы хоста, и правки с двух сторон дают рассинхрон состояния | P2 (по желанию) |

**Прошивка:** `.bin` в корень SD-карты (`Robin_nano.bin` для стоковой линейки /
`Robin_nano35.bin` для сборок Marlin), включить принтер — прошьётся сам.
`board_build.encrypt_mks` — бинарь шифруется под MKS-загрузчик, поэтому **прошить по USB нельзя
и не будет можно**. Всегда SD.

## 7. Риски

| Риск | Вероятность | Митигация |
|---|---|---|
| Стоковая прошивка не даёт GCode-контракта (закрытая MKS-сборка, конфиг из `robin_nano_cfg.txt`) | **средняя** | Фаза 0 обнаруживает это за 20 минут; ветка C — сразу шьём комьюнити-Marlin |
| `M500` пишет ошибку / не сохраняет | средняя | тот же Фаза-0 тест; ветка B |
| Обрывы CH340 (кабель, USB-хаб, сон ПК) | высокая | реконнект + идемпотентный коннект; не делать печать с ПК |
| Плата на самом деле KP Cheetah (Klipper) | низкая | Фаза 0 п. 0 — фото платы; тогда план другой (Moonraker API) |
| Рассинхрон состояния между тач-UI и приложением | средняя | урезать тач-UI; после коннекта всегда перечитывать `M503`/`M851`/`M420` |
| Износ flash-EEPROM от частых `M500` | низкая при дисциплине | явная кнопка сохранения, батчинг, счётчик записей |
| PA8 (управление BLTouch) физически не выведен на разъём | низкая | у Kingroon есть штатный комплект → выведен; уточняется в Фазе 0 |
| SmartScreen блокирует запуск на Windows | средняя | заложено в Фазу 5. Под macOS вопрос снят: там только браузер |
| **Управление нагревателями открыто в локальную сеть** | средняя, последствия высокие | §4: по умолчанию `127.0.0.1`, токен обязателен, клампинг на сервере, лимит частоты, аудит, в интернет не выставляем |
| Токен уходит по открытому HTTP внутри Wi-Fi | низкая на домашней сети | явно документировано; TLS — опция на потом |
| Управление с нескольких устройств одновременно → путаница | средняя | одна модель состояния в ядре, ярлыки устройств, аудит команд |
| Мак остаётся без кабеля и без Windows-ПК под рукой | — | кабель USB-C → USB-B (~₽500) либо мини-хост; см. §3 |

## 8. Отклонённые альтернативы

Подробно — [RESEARCH.md §7](RESEARCH.md#7-отклонённые-альтернативы-чтобы-не-возвращаться-к-спору).
Кратко:

- **Klipper** — идеально ложится на сценарий «принтер всегда подключён к ПК», но `klippy`
  Linux-only: Windows требует WSL2 + `usbipd-win` (устройство отваливается при переподключении
  USB), macOS не поддерживается вообще. Требование Windows + macOS это убивает.
- **OctoPrint как ядро** — тянет Python-стек, спроектирован под Raspberry Pi, плохо упаковывается
  в desktop.
- **Форк Pronterface** — UI на wx устарел; `printcore` берём как спецификацию, не как зависимость.
- **Своя прошивка** — не нужна: стандартный GCode-контракт Marlin даёт всё требуемое, а свой
  форк добавляет только риск.
